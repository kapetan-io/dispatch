1. **Orient.** Read the ticket, its comments, and the design it cites. The design decides what to build, so don't re-argue it. The ticket's statements of fact are guesses until you observe them. It was often written by an agent from memory, so its cause, repro, description of today's code, test recipe and what it says the design requires are claims. Check each claim your work depends on by running it, writing a failing test, or tracing the code. Check a design claim against the design itself. Skip claims that don't carry weight, and don't re-prove one that is plainly true. A claim that checks out needs no comment. For a bug, write the failing surface test first and run it to see it fail before you edit any source. A fix written in the same step as its test proves nothing. If it doesn't fail on main, write no fix, post what you ran on the ticket, and move it to Needs Human. When a claim is wrong, ask what it changes. If it only changes how to build, comment on the ticket with your evidence and keep going. If it changes what gets built, quote the ticket's claim next to what you saw in a ticket comment and move the ticket to Needs Human. Your final message is not the ticket, and a correction that appears only there is lost, so write the comment before you build on the claim. Every acceptance criterion must be observable at the surface. If one isn't, ask. A ticket already In Review has its PR open, so skip to step 7.
