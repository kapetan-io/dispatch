1. **Orient.** Read the ticket, its comments, and the design it cites. The design decides what to build, so don't re-argue it. The ticket's statements of fact are claims, often written by an agent from memory: a cause, a repro, what the code does today, a test recipe, "nothing open". Check each claim your work depends on by running it, writing a failing test, or tracing the code. For a bug, reproduce it with a failing surface test before changing code. No confirmed repro means no fix. If it doesn't reproduce on main, say so on the ticket and move it to Needs Human. A wrong claim about how to build it gets a note with your evidence, and you keep going. A wrong claim that changes what gets built goes to Needs Human. A ticket once told its worker to test with tickets the dispatcher would never read. Every acceptance criterion must be observable at the surface. If one isn't, ask. A ticket already In Review has its PR open, so skip to step 7.
