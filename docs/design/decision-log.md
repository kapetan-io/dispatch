# Workflow Decision Log

Decisions for the autonomous development workflow, written so a new session can continue without the chat history. The dispatcher's own design lives in `blueprint.md`, and this log lists the edits that blueprint still owes.

Three kinds of ticket appear below. The **feature ticket** holds the blueprint and carries the `design` label. The **review ticket** is its child, labeled `design-review`, where the autonomous review runs. **Build tickets** are the feature ticket's other children, one PR each.

## Glossary

- **herdr.** A terminal workspace manager for AI agents (`/opt/homebrew/bin/herdr`, 0.9.0). Each worker runs in a herdr workspace, and herdr reports each agent's status as idle, working, blocked, done or unknown.
- **treehouse.** A pool of git worktrees (`~/go/bin/treehouse`, v3.1.2). A tree is leased under a holder string, here always a ticket id, and returned to the pool when done.
- **captain.** The old coordinator skill this workflow retires. `blueprint.md` has the evidence against it.
- **dispatcher.** The stateless script specified in `blueprint.md`. `dispatch run`, in a herdr window you keep open, runs `dispatch tick` every 5 minutes.
- **phase.** Phase 1 is the design stage, and phase 2 is the build stage plus the dispatcher. "Advancing a phase" means moving from grill to review, or from review to build.
- **the grill.** The new interactive design skill. It is not the existing `grill-me` skill.
- **the review.** The new autonomous design-review skill, run on the review ticket.
- **kickoff.** The first prompt the launcher types into a new worker. It decides which skill the worker runs. No kickoff text exists yet.
- **working copy.** The review worker's local copy of the blueprint document, kept outside its worktree. Its path is not decided.
- **persona reviewers and code probes.** Reviewers that play a user of the design, such as an API consumer writing a client from the docs alone. Code probes are small checks a reviewer runs against the existing code to test what the blueprint claims. Both found real errors on ENG-189.

## Build stage (settled before 2026-10-07)

Each build worker runs these steps on its own build ticket.

1. **Orient.** Read the ticket, its comments, the feature ticket's comments and the blueprint. Every acceptance criterion must be observable at the surface. If one is not, ask you.
2. **Implement.** Every acceptance criterion gets at least one passing surface test, following the surface-testing skill. Tests may be written before or after the code. This is not TDD. Generic TDD prompting made small models worse (TDAD, arXiv 2603.17973), the number of tests written made no difference to resolution (Chen et al., arXiv 2602.07900), TDD helped Sonnet (TDDev, arXiv 2605.17242), and supplied tests help as a spec (Mathews and Nagappan, arXiv 2402.13521). Your own results with surface tests decided it.
3. **Test review.** A fresh agent, modeled on review-tests, checks the acceptance criteria and invariants against the tests and writes the missing ones. A new failing test is treated as a likely bug and fixed. Acceptance tests must go through the surface.
4. **Code review.** Three lenses, correctness, ticket fit and reader. Every finding is checked with evidence, a failing test or a code trace, before it is fixed or set aside, the same rule as step 7. In the ENG-228 pilot the worker set two correctness findings aside as low severity without checking them, and an outside review later proved three bugs on PR #4, two on those same paths (added 2026-10-08, ENG-231). A round that led to fixes is not clean, so the changed code gets another round. Both pilot workers stopped after one round with fixes (added 2026-10-08, ENG-233). Stop after one clean round or 3 rounds. Blockers that survive go to you.
5. **Verify.** Rebase onto main, rerun the tests, run the app.
6. **PR.** Written for the reviewer in the Purpose and Implementation format, not copied from the ticket. The title describes the change, not the ticket's title. It covers how the change was verified, the explainer link and `Fixes <build ticket>`. It has no "departures from the design" section, because a second account of the design next to the blueprint leaves readers to merge the two (dropped 2026-10-08). Enable auto-merge only when the base branch requires an approving review. Wait until Linear shows the PR linked on the ticket, then move the ticket to In Review, check again about 30 seconds later, and move it back if Linear reverted it. A visible link does not prove Linear's status change has landed. Linear's GitHub integration moves a ticket to In Progress when it links a new PR, and moved ENG-232 back 2.5 seconds after its worker set In Review. Turning that automation off needs admin rights, which the work setup lacks (added 2026-10-08, ENG-233).
7. **Feedback until merge.** Every review comment is a claim to verify with evidence, a failing test or a code trace. A confirmed claim gets fixed and a reply. An unconfirmed claim from a bot gets a reply with the evidence and is resolved. An unconfirmed claim from a person gets a reply with the evidence and goes to you as Needs Human. A flaky check gets its own ticket and a re-run. A real failure gets fixed.

- The feature ticket's comments are the shared channel for drift between build tickets. Public contract changes go to you.
- Workers run no `/loop`, cron or babysit-pr polling. The dispatcher is the only clock, and a nudge is a worker's only wake-up.
- **When the design is wrong** (settled 2026-10-08, from poteto's `architect` skill, phases D and E). A deviation from the design is a question to answer on the spot, not a change to absorb. Was the design wrong, was a requirement missed, or is the code overreaching? A pattern means the design is wrong. Her signs are the same workaround in unrelated places, many unrelated edge cases each needing a special branch, types that only compile with casts or `any`, reaching for a lock when the design said nothing was shared, callers needing to know the abstraction's internal rules, and the same deviation appearing more than once. When the pattern shows up, the worker stops patching. It posts what it found on the feature ticket, files a redesign review ticket under the feature ticket, and moves its own ticket to Needs Human.
  - The redesign review runs her redesign steps. It re-traces what has been built, redesigns as if the new facts had been known from day one, makes the new design smaller first, and runs the arena again. Then it runs the usual review and the split into pieces, and hands off for your approval like any review.
  - The redesign review ticket links to the build ticket whose findings triggered it and to the comment with the evidence, so the audit trail shows why the redesign exists. On your approval, the triggering build ticket's PR is closed, and every build ticket of the old design that has not merged is canceled with a comment linking to the redesign ticket. The new design's tickets start fresh.
  - Shipped work is never reverted. Pieces already merged stay, and the redesign starts from what is on main. Because the first piece blocks the rest, a redesign during the first piece cancels only unstarted tickets.

## Breakdown step (in progress)
